**Goal:** understand how a machine finds a website: its IP, its gateway, and how DNS turns a name into an address.

## 1. My lab network

| Fact | Value | Meaning |
|---|---|---|
| Private IP | `172.31.10.100/20` | My address inside the VPC (leased by DHCP). The public IP is mapped to this by AWS and does not appear in `ip a` |
| Interface | `ens5` | The network card |
| Gateway | `172.31.0.1` | The door out of my network (`default via` in `ip r`) |
| DNS server | `172.31.0.2` | The VPC resolver (VPC base address + 2) |
| MTU | `9001` | AWS jumbo frames (normal networks use 1500). Remember this for the MTU lab |
| DNS domain | `ap-south-1.compute.internal` | |

**Netplan file:** `/etc/netplan/50-cloud-init.yaml` (needs `sudo` to read, root-only).
- Generated by cloud-init at first boot, not written by me.
- Matches the NIC by MAC address, uses `dhcp4: true`, names it `ens5`.
- So IP, gateway and DNS come from AWS DHCP, not from this file.
- If a disk is cloned to a machine with a different NIC, a MAC-matched config can leave the network down.

**`netplan try`:** applies a config and auto-reverts unless I press ENTER. It is the safe way to change network config over SSH.

## 2. What happens on `curl example.com`

1. **DNS:** name becomes an IP. Can fail: name doesn't resolve (`NXDOMAIN`, timeout).
2. **TCP handshake:** SYN → SYN-ACK → ACK. Can fail: timeout (blocked/no route) or connection refused (nothing listening).
3. **TLS:** encryption is set up (https only). Can fail: certificate errors.
4. **HTTP:** `GET /` and the response. Can fail: 404, 500, 502, etc.

```
curl example.com
      |
      v
 1. DNS lookup      "what is the IP of example.com?"  -> 104.20.23.154
      |             can fail: NXDOMAIN, DNS timeout
      v
 2. TCP handshake   SYN -> SYN-ACK -> ACK  (to port 80 or 443)
      |             can fail: timeout (blocked) or refused (nothing listening)
      v
 3. TLS             agree on encryption keys (https only)
      |             can fail: certificate errors
      v
 4. HTTP            GET /  ->  200 OK + the page
                    can fail: 404, 500, 502
```

Support habit: when something fails, ask "which of these 4 boxes is broken?"

## 3. DNS lookup order on Ubuntu

```
app (curl/ping)
  -> /etc/nsswitch.conf   ("hosts: files dns" = check /etc/hosts first, then DNS)
  -> /etc/hosts           (local phone book)
  -> systemd-resolved     (127.0.0.53, local stub + cache)
  -> upstream DNS         (172.31.0.2)
```

## 4. Commands I used

| Command | What it shows | What I saw |
|---|---|---|
| `ip a` | Interfaces and IPs | `ens5` with `172.31.10.100/20`, `dynamic`, MTU 9001 |
| `ip r` | Routes. `default via` = gateway | `default via 172.31.0.1` |
| `ip neigh` | Recently seen local neighbours + MACs | Gateway and DNS show the same MAC (both are the VPC's virtual router) |
| `resolvectl status` | DNS servers, resolver mode | `stub` mode, DNS `172.31.0.2` |
| `ss -tulpn` | What is listening on which port | 22 (SSH), 80 (nginx), 53 on 127.0.0.53/54 (local DNS), UDP 68 (DHCP), UDP 323 on localhost (chrony time sync) |
| `ping -c 3 <target>` | Reachability and latency | See section 5 |
| `traceroute -n <name>` | Hops on the path | See section 5 |
| `dig name` | Full DNS answer (`status`, `ANSWER`, TTL, `SERVER`) | `NOERROR`, 2 A records, answered by 127.0.0.53 |
| `dig +short name` | Just the answer | |
| `dig @8.8.8.8 +short name` | Ask a specific DNS server | Same IPs as my own resolver |
| `dig +trace name` | Root → TLD → authoritative path | root → `.com` gtld → Cloudflare (`hera.ns.cloudflare.com`) |
| `dig +short MX / TXT / NS / CNAME name` | Other record types | See section 6 |
| `getent hosts name` | What apps see (follows nsswitch order) | |
| `resolvectl query name` | Where an answer came from | `Data from: synthetic` for a /etc/hosts entry |

## 5. Troubleshooting order and results

**Order:** gateway → internet by IP → DNS → app/port. Test nearest to farthest; the first failure shows the broken layer.

| Test | Result | Proves |
|---|---|---|
| `ping 172.31.0.1` | 0% loss, ~0.06 ms | Local network works |
| `ping 8.8.8.8` | 0% loss, ~1 ms | Internet works by IP |
| `ping example.com` | 0% loss, resolved to `172.66.147.243` | DNS works |

- If IP works but the name fails → DNS problem. If even `8.8.8.8` fails → network/route problem.
- TTL drops by 1 per router: `ttl=64` (gateway, directly connected), `117` (8.8.8.8), `57` (example.com).

**Traceroute notes:**
- Stars (`* * *`) in the middle are normal if later hops and the destination still reply. Some routers don't answer probes.
- Worry only if the trace never reaches the destination.
- The first visible hop was not my gateway `172.31.0.1`. It was inside AWS's own network.

## 6. DNS details

- `dig` showed `status: NOERROR` and 2 A records (`104.20.23.154`, `172.66.147.243`). Cloudflare returns several IPs for one name.
- **TTL:** my resolver showed 136, the authoritative TTL was 300. The difference is time already spent in the local cache.
- **IPv6 errors in `dig +trace`** (`network unreachable` on `2001:...` addresses) are normal here: this instance has no IPv6 (`dhcp6: false`). `dig` falls back to IPv4. One root server also timed out and `dig` moved on to another.
- **Record types:**
  - `MX gmail.com`: mail servers, lowest number = highest priority (5 first).
  - `TXT example.com`: SPF `"v=spf1 -all"` (no server may send mail for this domain) plus a verification token.
  - `NS example.com`: Cloudflare runs the DNS.
  - `CNAME www.github.com`: alias to `github.com.`

## 7. Experiment: fake `/etc/hosts` entry

I added `1.2.3.4 test.example.com`, then compared tools.

**My prediction:** `ping` and `getent` would use it, but plain `dig` would ignore it.
**What happened:** all three showed `1.2.3.4`.

| Command | Result |
|---|---|
| `ping test.example.com` | Tried 1.2.3.4 (timeout is expected, not a real server) |
| `getent hosts test.example.com` | `1.2.3.4` |
| `dig +short test.example.com` | `1.2.3.4` |
| `dig @8.8.8.8 +short test.example.com` | nothing |
| `dig @172.31.0.2 +short test.example.com` | nothing |
| `resolvectl query test.example.com` | `1.2.3.4`, `Data from: synthetic` |

**Why:** plain `dig` asks the local stub (127.0.0.53) = systemd-resolved, and systemd-resolved reads `/etc/hosts` itself and answers from it ("synthetic" = made up locally, never asked the network). `dig` does not read `/etc/hosts` itself, but the server it asks can.

**Lesson:** always note which server answered. `dig @8.8.8.8` bypasses the local path, `getent hosts` shows what apps see, and `resolvectl query` shows where an answer came from.

I removed the fake line afterwards and checked `/etc/hosts` was clean.

## 8. Check question

**Why can `dig` return the right IP while the app still fails?**

Because they can take different paths. `dig @8.8.8.8` skips my machine's lookup order, but an app follows `nsswitch.conf` (`files` first, then `dns`), so a wrong `/etc/hosts` entry, a stale cache, or a different resolver can break the app while `dig` looks correct. Apps can also prefer IPv6, use their own resolver or DNS-over-HTTPS (browsers), or go through a proxy. To find the split: compare `dig +short name`, `dig @8.8.8.8 +short name` and `getent hosts name`, and use `resolvectl query name` to see where the answer came from.

## 9. What I learned (2 lines)

1. The biggest lesson: `dig` and the app can take different paths. Plain `dig` asks my local resolver (127.0.0.53), which reads `/etc/hosts`; `dig @8.8.8.8` skips my machine; apps follow `nsswitch.conf` (`/etc/hosts` first, then DNS). So a fake hosts entry can make an app fail while `dig` looks fine, and I now check where an answer came from (`dig @8.8.8.8`, `getent hosts`, `resolvectl query`).
2. If a website works by IP but not by name, I check DNS first. `NXDOMAIN` means the name doesn't exist, a timeout means my DNS server isn't answering. The commands I'll use most are `ss -tulpn` (what is listening), `ip neigh` (local neighbours) and `dig` (status, answer, which server).

### If a site works by IP but not by name: my checklist

1. `dig +short name`: does DNS answer? (`NXDOMAIN` = name doesn't exist; timeout = DNS server not answering)
2. `getent hosts name`: what do apps see?
3. `dig @8.8.8.8 +short name`: what does a public server say?
4. `resolvectl query name`: where did the answer come from (network, cache, synthetic)?
5. If the answers differ between these, the problem is local: `/etc/hosts`, `nsswitch.conf`, or the resolver config.

### `dig` cheat sheet (the only 3 I need to remember)

- `dig name`: full answer (status, ANSWER, TTL, SERVER)
- `dig +short name`: just the IP(s)
- `dig @8.8.8.8 +short name`: ask a specific server (the part after `@` is who I ask; if I leave it out, I ask my own machine's resolver)
